# Production Ecommerce Platform — Master Development Prompt

You are the lead software architect and senior full-stack engineer responsible for building a production-ready ecommerce platform.

## 1. PROJECT OBJECTIVE

Build a completely functional, production-quality ecommerce platform from scratch.

The initial target market is Pakistan/local commerce.

The architecture MUST be designed from day one so the same application can later support international markets without requiring a complete rewrite.

This is NOT a prototype, mockup, tutorial project, or static frontend.

Build a real application with:

* Product management
* Product variants
* Categories
* Inventory
* Customers
* Authentication
* Shopping cart
* Checkout
* Orders
* Payments
* Cash on Delivery
* Coupons/discounts
* Shipping
* Addresses
* Reviews
* Wishlist
* Admin dashboard
* Order management
* Inventory management
* Customer management
* SEO
* Analytics
* Email notifications
* Error handling
* Security
* Validation
* Responsive UI
* Performance optimization

The application must be deployable to Vercel.

# 2. TECHNOLOGY STACK

Use the following stack unless there is a strong technical reason to change something.

## Core

* Next.js
* App Router
* TypeScript
* React
* Tailwind CSS
* shadcn/ui

## Backend/application

Use Next.js as the application/backend layer.

Use:

* Server Components by default
* Server Actions where appropriate
* Route Handlers for APIs/webhooks
* Zod for validation

Do NOT create a separate Express/NestJS backend unless there is a clearly documented reason.

## Database

* PostgreSQL
* Supabase
* Drizzle ORM

Use PostgreSQL as the primary source of truth.

Do not use Supabase as a replacement for application/business logic.

Keep business logic inside the application layer.

## Authentication

Use Supabase Auth.

Support:

* Email/password
* Email verification
* Password reset
* Session management
* Customer accounts
* Admin authentication

Design authorization around roles.

At minimum:

* customer
* admin

The architecture should allow future roles such as:

* manager
* inventory_manager
* support
* marketing

## File storage

Do not store product images inside the Git repository.

Design the image layer so it can use:

* Supabase Storage initially
* Cloudinary later if required

Create an abstraction around media storage so switching providers does not require rewriting product functionality.

## Deployment

Primary deployment target:

* Vercel

Database:

* Supabase PostgreSQL

DNS/security:

* Cloudflare

# 10. PAYMENT ARCHITECTURE

Create a payment-provider abstraction.

Example conceptual interface:

```ts
interface PaymentProvider {
  createPayment(): Promise<PaymentResult>
  verifyPayment(): Promise<VerificationResult>
  refundPayment(): Promise<RefundResult>
}
```

Initial payment methods:

* Cash on Delivery
* Placeholder local payment gateway abstraction

Future providers:

* Stripe
* PayPal
* Regional payment providers

The order system must not depend directly on a specific payment provider.

Implement webhooks securely.

Webhook handling must be:

* authenticated/verified
* idempotent
* logged
* retry-safe

Never trust payment status sent directly from the browser.

# 35. IMPORTANT DEVELOPMENT RULES

Never:

* invent credentials
* invent API keys
* hard-code secrets
* expose service-role keys
* trust client-side prices
* trust client-side payment status
* skip server validation
* directly modify production data
* disable security to make something work
* create fake successful payment responses
* create fake shipping confirmations
* claim an integration works without actually testing it

If a third-party integration requires credentials that are unavailable:

1. Build the provider interface.
2. Implement the integration where possible.
3. Use a clearly isolated development/mock provider only for local testing.
4. Document exactly what credentials are required.
5. Never pretend the production integration is complete.
